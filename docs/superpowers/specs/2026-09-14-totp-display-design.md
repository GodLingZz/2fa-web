# TOTP 验证码即时展示设计

## 目标

用户确认使用 Token 后立即展示当前标准 TOTP 验证码，不再等待下一个 00 秒或 30 秒边界；倒计时使用服务端返回的真实失效时间。当前验证码失效后自动请求下一个时间片的验证码，第二个验证码展示完整 30 秒，结束后沿用现有失效锁定界面。

## 已确认约束

- 必须兼容标准 TOTP 30 秒时间片，不能人为延长首码有效期。
- 首码的展示时长是当前时间到下一个 TOTP 边界的真实剩余秒数，可能小于 30 秒。
- 首码失效时只允许自动刷新一次，得到第二个验证码。
- 第二码按标准时间片展示完整 30 秒。
- 第二码结束后保持当前项目的失效逻辑：显示 `--- ---`、禁用复制、显示“口令已失效”、倒计时为 `0s`。
- 不在浏览器端保存或生成 TOTP secret；继续由 `/api/token/verify` 生成验证码。

## 当前实现与问题

`2fa-verify.html` 在确认 Token 后调用 `getSecondsToNextTotpBoundary()`，进入等待区，直到边界才请求验证码。这导致用户必须等待，并且现有页面只展示一个验证码。服务端已经返回 `timeLeft` 和 `expiresAt`，可以直接支撑即时展示和准确倒计时。

## 方案

只调整公开页前端会话状态，不改 TOTP 算法、数据库结构或服务端安全语义：

1. 确认 Token 后立即调用 `/api/token/verify`，服务端按当前时间片返回首码、`timeLeft`、`expiresAt`。
2. 前端以 `expiresAt - Date.now()` 计算倒计时，并用带会话 ID 的定时器更新 UI，避免请求延迟造成多显示。
3. 首码倒计时到零时自动再次调用接口，接口生成下一个标准时间片的验证码。
4. 第二次成功响应后显示第二码，倒计时以其 `expiresAt` 为准；响应若恰好跨边界则显示服务端实际剩余值，确保不展示已失效验证码。
5. 第二码结束后调用已有 `lockExpiredCode()`，不再发起第三次刷新。
6. 返回输入页、请求失败或会话过期时清理定时器，并通过 `activeSessionId` 丢弃旧请求响应。

## 错误处理

- 首码请求失败：沿用现有错误提示并返回 Token 输入页。
- 第二码请求失败：沿用现有错误提示并返回 Token 输入页。
- 用户返回或重复确认：清理旧计时器，旧异步响应不得改变新页面。
- 倒计时采用绝对时间而非累计 `--`，应对浏览器后台节流和短暂卡顿。

## 验收标准

- 任意秒数点击确认后，等待区不出现，首码立即可见。
- 首码的倒计时等于服务端 `expiresAt` 的真实剩余时间，边界时自动刷新。
- 首码结束后只请求并展示一个第二码，第二码不被截断，最多展示 30 秒。
- 第二码结束后页面与现有失效锁定 UI 一致，复制按钮不可用。
- 网络失败、返回输入页、重复操作不会留下计时器或旧码覆盖。
- 本地 Playwright/浏览器检查和线上正式地址检查均通过。
